# Slack-inspired UI restyle

**Date:** 2026-07-27
**Status:** Approved, ready for implementation planning
**Scope:** `apps/web` and `apps/mobile`

## Summary

Kitchen AI's web and mobile apps currently look like two different products. Web is
green-on-white (`#1f7a4d`); mobile is terracotta-on-cream (`#C4562B`). This restyle
adopts a single Slack-inspired visual language across both: aubergine primary on a
cream canvas, pill buttons, sharp form fields, and a status palette decoupled from the
brand colour.

The source is `DESIGN.md` at the repo root, generated by `npx getdesign@latest add slack`.
That document describes a *marketing site*. Kitchen AI is a logged-in product app, so
this spec records which parts transfer, which are adapted, and which are deliberately
dropped.

This is a **restyle, not a redesign**. No layout changes, no new screens, no navigation
restructure, no component API changes. Same markup, same props, same tests.

## Why now

Two defects surfaced while designing this, and both are fixed as part of the work:

1. **The warning badge is illegible.** `Badge tone="warning"` is `bg-accent/20 text-accent`
   — amber text on pale amber — measuring **1.87:1** against a WCAG AA minimum of 4.5:1
   for small text. It has been shipping this way.
2. **Status colour is coupled to brand colour.** `Badge tone="success"` is literally
   `bg-primary/15 text-primary`. "Success" is green only because the brand happens to be
   green. Any brand change silently breaks freshness colour-coding — turning every
   "Fresh" and "Planned" badge purple, which in a food app reads as spoiled.

## Design principles

- **Status is not brand.** Success, warning and danger get explicit tokens. Aubergine is
  reserved for brand identity and calls to action. This does not violate the spec's
  "no third accent" rule — that rule governs *brand* accents, and the spec defines its
  own `semantic-success` and `semantic-error` values.
- **Measure, don't eyeball.** Every colour pair in this spec was computed against WCAG.
  Where the source spec's own value fails, we deviate and say so.
- **Latin typographic devices stay on Latin.** Negative letter-spacing and uppercase are
  Latin conventions. Arabic is cursive and caseless; applying them globally damages it.
- **YAGNI.** Marketing devices with no home in a product app are dropped, not adapted.

### Soft chips carry a solid border

A light tint alone cannot be both legible under its own text *and* distinguishable from
every surface it may land on. Measured: `--warning-soft` `#f3eee6` sits 4 channel-steps
from the cream canvas — a warning chip on the canvas would be invisible — and pushing the
tint darker until it separates drops `--success` and `--danger` below 4.5:1 against their
own text. There is no tint value that satisfies both.

So every soft chip and tinted surface carries a **1px border in the solid status colour**.
That reuses tokens already verified for text contrast, adds none, and clears WCAG 1.4.11's
3:1 for UI boundaries on every surface (worst case 4.60:1). A 25% border was measured
first and rejected at 1.35:1.

`Badge` becomes `bg-{tone}-soft text-{tone} border border-{tone}`. `ReviewList`'s
low-stock card already has a border of this kind; it goes from `border-accent/50` to a
solid `border-warning`.

### Tints are solid tokens, not opacity

Tinted backgrounds behind text become **solid `*-soft` tokens** rather than
`bg-primary/15`-style opacity utilities. Three reasons:

- Tailwind v4 compiles `/8` to `color-mix(in oklab, … 8%, transparent)`, so the rendered
  value is not the sRGB alpha blend the contrast maths assumes. Solid tokens make the
  measured number the shipped number.
- It mirrors mobile's existing `primarySoft` / `successSoft` / `warnSoft` / `dangerSoft`
  convention, so both platforms name the same concept the same way.
- The contrast test can assert on literal token pairs instead of recomputing composites.

Tint density drops from 15–20% to the equivalent of **8%** in light and **18%** in dark;
the denser tint was the main cause of the contrast failures.

### Fields

Inputs go 8px → **4px** (`rounded-lg` → `rounded`). Sharp fields against 90px pills is
deliberate in the source spec and is a large part of why the language reads as Slack
rather than generically rounded. Applies to `Input`, `Select` (`FIELD_BASE`) and
mobile `Field.tsx`.

Mobile's `radius` scale has no 4px entry — it is `sm: 8, md: 12, lg: 18, pill: 999` — so
it gains `xs: 4`, and `Field.tsx:37` moves from `radius.md` to `radius.xs`. Only the field
moves; the other 25 `radius.*` call sites are unaffected.

### Everything else

- **Cards: no change.** Already `rounded-2xl` (16px) = the spec's `rounded.xl`.
- **Badges:** stay pill; padding `px-2.5 py-0.5` → `px-3 py-1`; solid `*-soft` background
  plus a 1px border in the matching status colour.
- **IconButton:** `rounded-lg` → `rounded-full`.
- **Sidebar nav rows:** stay at 8px. The pill rule governs buttons; Slack's own sidebar
  uses soft rectangles.
- **Filter chips:** already `rounded-full`. No change.

### Elevation

Cards keep `shadow-sm` on the cream canvas — white-on-cream plus a hairline border
already separates them. The auth card takes the spec's level-1 shadow
(`0 5px 20px rgba(0,0,0,0.1)`) as the single lifted surface in the app.

**Latin-only tracking is a hard requirement.** Arabic is a cursive script whose letters
join; CSS `letter-spacing` forces gaps into those joins and visibly degrades legibility.
Arabic also has no letter case. Tracking is applied under `:root:lang(en)` and reset to
`normal` in the existing `:root:lang(ar)` block, which already overrides the font family
and line-height. On mobile, `SCALE` gains a `letterSpacing` field that `typography(locale)`
zeroes when `locale === 'ar'`, mirroring how it already switches line-height.

Latin body leading moves to **1.55**. Arabic stays at **1.85**.

## Semantic corrections

Every place a component names the brand but means a status, or reaches for an opacity
tint the theme should own. An earlier draft of this spec tabulated thirteen of these.
A full sweep of the codebase found **thirty-five**, and the omissions were not cosmetic:
every `text-primary` that renders actual text fails WCAG in dark mode, because
`--primary` `#8a4d90` is a *fill* colour. Measured against the surfaces it lands on:
**2.00:1** on `--primary-soft`, **2.57:1** on `--muted`, **2.86:1** on `--background`,
**3.21:1** on `--canvas`. `--primary-text` exists precisely to absorb this, so it must be
applied at every such site, not a sample of them.

### The three mechanical rules

Applied uniformly, these cover every row below:

1. **Aubergine that renders text or an icon** → `text-primary-text` (never `text-primary`,
   which is reserved for fills and focus rings).
2. **Opacity tint behind text** (`bg-primary/5` … `/20`) → the matching solid `*-soft` token.
3. **Opacity border** (`border-primary/40`, `/50`) → the matching solid token.

Two sites are deliberately **excluded**: `settings/SettingsView.tsx:165` and
`shopping/ShoppingView.tsx:135` put `text-primary` on a native `<input type="checkbox">`,
where it sets `color` — a property native checkboxes ignore. It renders nothing today and
would render nothing after. Changing it to `accent-primary` would alter appearance, which
this restyle does not do.

## Loose ends fixed alongside

- **`apps/web/src/app/layout.tsx`** pins `theme-color` to `#ffffff` / `#0b0f0d`. These are
  the only hardcoded colours in the web app outside `globals.css` and would leave a white
  notch above a cream page in mobile Safari. They become `#f4ede4` / `#140e15`.
- **`apps/mobile/src/app/recipe/[id]/cook.tsx`** paints its background with `colors.text`
  (lines 27, 38) and its text with `colors.surface` / `colors.surfaceAlt` (lines 41, 64,
  69) — inverted by accident, not intent. Reading a *surface* token as a *text* colour
  works only by coincidence and breaks the moment either value moves. Mobile gains two
  tokens so the intent is stated: `surfaceInverse` `#1D1D1D` for the background, and
  `textInverseMuted` `#C7C7C7` for the secondary lines. Primary text uses the existing
  `textInverse`. Measured on `surfaceInverse`: `textInverse` **16.86:1**,
  `textInverseMuted` **9.97:1**.

## Dropped from `DESIGN.md`

- **Pastel-mesh gradients.** The spec's entire depth language is blurred peach/lavender/
  green backdrops behind floating product screenshots. Behind a working inventory table
  that is noise. Cream canvas plus white cards does the same job.
- **All-caps eyebrows** (`micro-cap`, 12px/700, `+0.96px` tracking). There is no uppercase
  text anywhere in the app today, and Arabic is caseless — an eyebrow would style in one
  language and not the other.
- **Marketing display tiers** (64/58/50px). No home in a logged-in app.
- **Marketing components** — pricing cards, aubergine band cards, stat callouts,
  customer-logo strips.

## Implementation order

Four steps, each independently verifiable:

1. **Tokens.** `globals.css` and `mobile/theme/index.ts` only. The app goes aubergine in
   one commit.
2. **Primitives.** `Button`, `Input`, `Badge`, `IconButton`, `Card` — pill radius, 4px
   fields, solid `*-soft` tints with status-coloured borders, 700 labels.
3. **Semantic corrections.** The ~35 lines tabulated above, applied by the three
   mechanical rules.
4. **Shell and type.** Cream canvas, lavender auth, Latin-only tracking, 1.55 body
   leading, `theme-color` metas, cook-mode token fix.

## Verification

**Already confirmed while writing this spec** (Tailwind v4.3.3, compiled via the
`tailwindcss` compiler API — not assumed):

- `rounded` resolves to exactly `0.25rem` (4px), `px-7` to 28px, `h-12` to 48px. The
  spec's numbers are reachable with stock utilities.
- `bg-canvas`, `bg-canvas-lavender`, `text-success`, `border-warning/50` and
  `hover:bg-primary-press` all generate correctly from `@theme inline` custom tokens.
- All 54 colour pairs in this document were computed against WCAG rather than eyeballed,
  and all pass. That pass only came after four failures the first run surfaced: white on
  the dark danger fill (2.31:1), aubergine as outline-button text in dark (2.86:1), and
  two tints indistinguishable from the surfaces they sit on. The `--primary-text`,
  `--danger-foreground` and soft-chip-border decisions all came out of that run.

**Existing tests must stay green untouched.** No test in either app asserts on a class
name and there are no snapshots. If the 29 web or 68 mobile tests break, that is a real
regression, not churn.

**A committed contrast test.** The amber badge shipped at 1.87:1 because nothing was
watching. Port the script used to write this spec into a unit test asserting, for both
themes:

- `foreground`, `muted-foreground` and `link` against every surface they can land on
  (`canvas`, `background`, `muted`, and `canvas-lavender` in light) — 4.5:1.
- `primary-foreground` on `primary` and on `primary-press` — 4.5:1.
- `danger-foreground` on `danger` — 4.5:1.
- Each status colour on its own `*-soft` background — 4.5:1.
- `primary-text` on `primary-soft`, on `background` and on `canvas` — 4.5:1 / 3:1.
- Each status colour as a chip border against `canvas` and `background` — 3:1.

Because tints are solid tokens, the test reads literal values and needs no compositing
maths. It parses `globals.css` itself rather than duplicating the values, so the CSS
stays the single source of truth and the test cannot silently drift from it. It must be
shown to **fail against the current palette** before the token change lands; that is the
proof it works. It should catch at least the 1.87:1 warning badge.

Mobile gets the equivalent, importing `colors` directly: every text token on every
surface it lands on, `textInverse` and `textInverseMuted` on `surfaceInverse`, each
status on its `*Soft`, and `textInverse` on the `primary` / `danger` fills.

**A usage guard.** Contrast tests check the palette; they cannot see a component reaching
for the wrong token. The eleven dark-mode failures this spec's first draft missed were all
of that kind — correct tokens, wrong site. A source sweep asserts that `text-primary`
(as opposed to `text-primary-foreground`) and `bg-primary/<n>`-style opacity tints do not
reappear in `apps/web/src`, with the two inert checkbox lines listed as explicit
exceptions. Without it, the next component to be written re-introduces a 2.86:1 label and
nothing notices.

**Route sweep.** All 11 web routes return 200 in both `en` and `ar`, in light and dark.

**Full gate.** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` across all
9 packages.

## Out of scope

No layout changes, no new screens, no navigation restructure, no component API changes,
no mobile dark theme. If a page's structure looks wrong after the restyle, that is a
separate conversation.
